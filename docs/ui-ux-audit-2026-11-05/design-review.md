# 전체 화면 디자인 검토와 적용 제안

## 검토 범위와 전제

홈 대표 이미지 이후 합의한 디자인을 다른 화면에도 적용하기 위한 검토예요. 현재 화면 코드와 기존 감사의 실제 화면 37장을 바탕으로, 제안 → 반문 → 조정 순서로 검토했어요. 이번에 새 UI를 구현하거나 추가 실기기 검증을 수행한 것은 아니에요. 이미지 시안은 디자인 방향이며 실제 화면의 크기 검증 결과가 아니에요.

기능 추가, 라우트 변경, 저장 구조 변경, 설문 분기 변경, AI 동의/인증/검증 변경은 제안하지 않아요. 앞서 합의한 뒤로가기와 명시적 저장 개선은 별도 동작 작업으로 유지하고, 시각적 변경 때문에 동작이 바뀌지 않게 분리해요.

## 공통 결론

따뜻한 밝은 배경, 흰색 정보 영역, 짙은 녹색과 큰 글씨를 유지해요. 홈의 카드 형태를 모든 화면에 복제하지 않고, 화면 역할별로 같은 디자인 언어를 사용해요.

| 역할 | 공통 표현 | 피할 표현 |
|---|---|---|
| 실행 | 채워진 주요 버튼, 명확한 보조 버튼 | 배경 위에 글자만 있는 행동 |
| 이동 | 경계가 있는 메뉴 행 또는 카드와 화살표 | 제목인지 링크인지 모호한 글자 |
| 선택 | 단일 원형, 복수 사각 체크, 선택 상태 윤곽 | 상태 표시를 선택 버튼처럼 표현 |
| 상태 | 짧은 문구와 필요 시 옅은 비조작 배지 | 상태 배지 안에 ‘하기’ 같은 실행 문구 |
| 읽기 | 소제목과 넉넉한 문단 간격 | 문단마다 카드와 테두리 추가 |
| 펼치기 | 경계가 있는 보조 영역과 펼침 표시 | 눌러보기 전까지 영역을 알 수 없는 문구 |
| 위험 행동 | 구분된 영역과 위험 색, 기존 확인 유지 | 일반 버튼과 같은 녹색으로 강조 |

버튼의 ‘주요/보조’는 색만 다른 것이 아니에요. 크기와 위치, 주변 간격까지 함께 정해요. ‘화면당 주요 행동 하나’는 모든 상황에 억지로 적용하는 규칙이 아니에요. 동의/거절처럼 대등하게 선택할 권리가 필요한 상황에서는 두 행동을 모두 충분히 알아볼 수 있게 해요.

## 화면별 자기 검토

### 1. 첫 실행과 단계 선택

**질문:** 차분하게 만들겠다며 시작 버튼과 선택지를 흐리게 만들고 있지 않나요?

**판단:** 소개는 장식보다 앱의 역할과 시작 행동이 중심이어야 해요. 단계 선택의 긴 설명까지 모두 굵게 하면 위계가 사라져요.

**제안:** 상단 브랜드는 작게, 제목은 충분히 크게, 설명은 본문 굵기, 시작은 채워진 버튼으로 통일해요. 단계 선택 행은 흰색과 얇은 테두리로 영역을 보이고, 선택 후에만 녹색 테두리와 체크를 사용해요. 라벨과 보조 설명의 굵기를 구분해요.

**재검토:** 선택 전에도 어떤 선택지가 정답처럼 보이지 않아야 해요. 선택하지 않은 항목을 흐리게 만들지 않아요. 회원가입이나 새 단계를 추가하지 않아요.

관련: `features/onboarding/onboarding-screen.tsx`, `features/start/stage-screen.tsx`, `components/selection-row.tsx`.

### 2. 개인화 설문과 완료 안내

**질문:** 여러 질문 화면의 제목 위치와 버튼 위치가 달라 길을 잃게 만들지 않나요?

**제안:** 질문 제목 → 짧은 설명 → 선택 영역 → 다음 버튼의 리듬을 통일해요. 선택 영역과 다음 버튼 사이 여백은 구분하되, 작은 화면에서 과한 빈 공간을 만들지 않아요. 긴 선택 문구는 높이가 늘어나도록 해요.

**재검토:** 모든 다음 버튼을 화면 맨 아래 고정하면 글자 확대나 키보드와 겹칠 수 있어요. 고정 배치는 실기기 검증 없이 일괄 도입하지 않아요. 분기형 질문에 임의의 전체 진행률을 붙이지 않아요.

완료 안내는 제목과 간결한 설명 중심으로 유지해요. 돌봄기록 안내의 ‘확인했어요’는 기존대로 홈으로 이동하고, 기능 소개와 외부 전송 동의는 계속 분리해요.

관련: `features/preparation/intro-screen.tsx`, `questions-screen.tsx`, `completion-screen.tsx`, `app/guide.tsx`.

### 3. 네 단계 홈

**질문:** 방문조사 홈을 예쁘게 만들었다고 다른 단계에도 빈 일정 카드를 넣어야 하나요?

**답:** 아니에요. 홈의 공통 구조만 맞추고 각 단계의 핵심 정보는 기존 조건 그대로 유지해요.

- 신청 전: 현재 단계 제목과 신청 준비 목록이 중심이에요.
- 방문조사 대기: 일정 → 질문 안내 → 확인 목록 → 준비 목록 순으로 정리해요.
- 결과 대기: 소견서 상태와 기한이 중심이에요. ‘상태 수정’도 경계가 있는 보조 버튼으로 바꿔요.
- 결과 수령: 실제 선택한 결과에 맞는 목록을 유지하고, 인정/불인정/내용 모름에 같은 문구를 억지로 쓰지 않아요.

단계 변경은 제목 위의 작은 보조 버튼으로 분리하되 글자만 놓지 않아요. 체크리스트 전체가 이동 영역이고 우측은 상태만 표시해요. 번호를 제거하고 완료 표시와 문구로 구분해요. 아직 답하지 않음, 명시적 미완료, 판단 어려움의 저장 의미는 임의로 합치지 않아요. ‘아직 답하지 않았어요’가 좁은 오른쪽에 안 들어가면 글자를 줄이지 않고 상태를 항목명 아래로 옮겨요.

**재검토:** 완료 항목을 지나치게 흐리게 하거나 자동으로 접으면 조회와 수정이 어려워져요. 읽기 가능한 대비와 기존 표시 순서를 유지해요. 목록 상태와 이동 화살표를 별도 버튼 두 개처럼 만들지 않아요.

관련: `features/home/home-screen.tsx`, `features/preparation/checklist.tsx`, `features/medical/ui.tsx`.

### 4. 체크리스트 상세

**질문:** 공식 링크와 완료 버튼이 경쟁하고 있지 않나요?

**제안:** 제목 → 핵심 안내 → 필요한 보충 설명 → 공식 안내 버튼 → 내 상태 선택과 저장으로 구역을 나눠요. 공식 안내와 관련 서식은 보조 버튼, 상태 선택은 선택 영역, 저장은 주요 버튼으로 구분해요. 완료 상태는 별도 상태 영역에서 보여줘요.

**재검토:** 안내문을 짧게 만들겠다고 중요한 공식 설명을 삭제하지 않아요. 데이터와 설명 내용은 유지하고 배치만 정돈해요. 두 가지 완료/미완료 정책은 일반 체크리스트에 적용하며 ‘요청받은 준비물 없음’ 같은 기존 예외를 제거하지 않아요. 명시적 저장 동작 변경은 이미 합의한 별도 개선으로 다뤄요.

관련: `features/preparation/detail-screen.tsx`.

### 5. 의사소견서 상태와 기한

**질문:** 날짜나 상태가 누를 수 있는 글자인지 사용자가 알아볼 수 있나요?

**확인:** 현재 `MedicalSummary`의 ‘상태 수정’과 기한 제목은 경계 없는 터치 영역이에요. 기한 입력의 ‘아직 안내받지 못했어요’도 평소 배경이 투명해요.

**제안:** 상태 요약을 하나의 정돈된 정보 영역으로 묶고, 수정은 별도 보조 버튼으로 표시해요. 기한 수정은 날짜가 포함된 경계 있는 이동 행으로 표시해요. ‘날짜 저장’과 ‘아직 안내받지 못했어요’는 각각 명확한 주요/보조 버튼을 사용해요.

**재검토:** 소견서 상태는 일반 체크리스트보다 의미가 세분화돼 있어요. 제출 전/제출 여부 모름/제출 제외를 단순한 미완료로 통합하면 안 돼요.

관련: `features/medical/screen.tsx`, `features/medical/ui.tsx`.

### 6. 방문조사 질문 살펴보기

**질문:** 내용을 떠올리는 안내가 답변 입력 화면처럼 보이지 않나요?

**제안:** 질문 위치를 작은 정보로, 질문 자체를 가장 크게, 떠올릴 기준을 편한 본문으로 보여줘요. 선택 박스나 빈 입력칸처럼 보이는 장식은 사용하지 않아요. 다음은 주요 버튼, 나가기는 명확한 보조 버튼으로 구분해요.

**재검토:** 완료 체크를 개별 답변의 정확성이나 준비 정도로 오해하지 않게 해요. 새 답변 입력, 점수, 진행률을 추가하지 않아요. 뒤로와 나가기 분리는 기존 합의 범위로만 구현해요.

관련: `features/visit-walkthrough/screen.tsx`.

### 7. 기록 탭과 작성 방법 선택

**질문:** 모든 진입 카드가 크고 설명도 길어 실제 작성 진입이 느리지 않나요?

**제안:** 현재 작성/돌아보기의 두 진입 기능을 유지하고 카드의 내부 여백, 제목, 설명 길이를 맞춰요. 직접 기록/질문 기록 선택은 두 행의 크기와 강조를 대등하게 유지해요. 작성 중인 기록은 분리된 보조 메뉴로 보여줘요.

**재검토:** ‘오늘 기록하기’를 어디에나 반복하면 홈에서 즉시 기록으로 보내지 않겠다는 기존 흐름이 깨져요. 새 바로가기나 자동 이동을 만들지 않아요.

관련: `features/records/records-browser.tsx`, `situation-screen.tsx`.

### 8. 직접 기록과 질문 기록

**질문:** 입력란은 잘 보이지만 추가 입력 기능은 글자처럼 방치돼 있지 않나요?

**확인:** `SubtleButton`의 평소 배경은 투명하고 테두리도 없어요. ‘다른 내용 직접 적기’, ‘조금 더 덧붙이기’, 불확실성 항목 펼치기가 여기에 해당해요.

**제안:** 이 기능들을 얇은 경계가 있는 보조 행으로 통일해요. 펼침 표시는 오른쪽에 일정하게 두고 열린 내용은 바로 아래 같은 구역에 배치해요. 단일/복수 선택의 도형을 구분하고, 직접 입력은 충분한 높이와 유형별 예문을 제공해요.

**재검토:** 선택 카드와 입력 보조 기능을 같은 모양으로 만들면 답변으로 오해해요. 선택지는 오른쪽 선택 도형, 보조 기능은 펼침 아이콘으로 구분해요. 불확실성 선택을 단순 미완료로 바꾸거나 입력 문장을 임의로 다듬지 않아요.

관련: `features/records/interview-question.tsx`, `situation-screen.tsx`, `components/action-controls.tsx`.

### 9. 미리보기와 기록 상세

**질문:** 원문과 AI 요약이 같은 카드면 어느 것이 작성한 내용인지 알아볼 수 있나요?

**제안:** 원문 영역에는 날짜와 유형을 함께 모으고 본문을 가장 편하게 읽게 해요. AI 요약은 ‘AI 한 줄 요약’ 표기를 유지하고 작은 색 차이나 경계로 구분해요. 미리보기의 저장은 주요 버튼, 수정은 보조 버튼으로 유지해요. 상세의 삭제는 수정과 떨어진 위험 영역으로 구분해요.

**재검토:** AI 요약을 원문보다 크게 강조하면 사실 확인 흐름이 약해져요. 요약이 없어도 원문을 바로 읽을 수 있어야 해요. 접근 코드와 동의 카드를 상세에 다시 넣지 않아요.

실패/생성 중/미사용 상태의 카드 높이가 급격히 튀지 않게 하되, 설명을 고정 높이로 잘라 숨기지 않아요.

관련: `features/records/situation-screen.tsx`, `ai-controls.tsx`.

### 10. 기록 목록, 초안, 캘린더

**질문:** 날짜, 유형, 가상 기록 표시, 본문이 모두 비슷한 무게로 보이지 않나요?

**제안:** 날짜 그룹 → 시간과 유형 → 요약 순으로 위계를 정리해요. 가상 기록 표시는 작은 보조 정보로 유지해요. 카드 전체가 이동 영역이고 화살표로 이동을 알리므로 ‘자세히 보기’를 별도 버튼처럼 중복 강조하지 않아요. 기간 선택은 경계 있는 필터 버튼으로, 페이지 이동은 보조 버튼으로 분명히 보여줘요.

**재검토:** 요약 가독성을 위해 날짜/유형을 너무 작게 줄이면 안 돼요. 긴 유형명은 한 줄 강제 대신 자연스럽게 줄바꿈해요. 새 유형 필터를 추가하지 않고 현재 기간/날짜 탐색을 유지해요. 초안은 작성 중이라는 표시와 이어쓰기 기능을 유지해 저장 완료 기록과 구별해요.

관련: `features/records/records-browser.tsx`, `review-screen.tsx`, `situation-screen.tsx`, `components/month-grid.tsx`.

### 11. 보고서 기간 선택과 저장 목록

**질문:** 선택 기간보다 안내 박스들이 더 크게 보이지 않나요?

**제안:** 7/30/90일 왼쪽 정렬과 간격을 유지하고 시작일, 종료일, 포함 건수를 한 정보 구역으로 정리해요. 생성 버튼 바로 아래에는 실행을 막는 이유와 해결 행동을 연결해요. 여러 이유가 있어도 각각을 큰 녹색 카드로 반복하는 대신 한 상태 영역 안에서 읽기 쉽게 구분해요.

저장 목록은 기간과 생성일, 건수를 먼저 보여주고 열기를 중심 행동으로 둬요. 삭제는 별도 구분된 보조 위험 버튼으로 유지해요.

**재검토:** 안내를 한 개로 줄이겠다고 다른 장애 원인을 숨기지 않아요. 저장된 보고서 열기와 새 AI 생성을 시각적으로도 구분하고, 재생성 기능이나 새 호출을 추가하지 않아요.

관련: `features/records/reports-screen.tsx`, `report-readiness.ts`.

### 12. 보고서 읽기와 PDF 행동

**질문:** 본문보다 관리 버튼이 많아 보고서를 읽는 화면으로 느껴지지 않나요?

**확인:** 상세에서 PDF 공유/인쇄/파일 저장/보고서 삭제/목록으로가 이어져요. 본문도 섹션마다 같은 카드로 묶여 있어요.

**제안:** 상단 기간/건수/생성일은 간결하게 묶고, 본문은 소제목과 문단 간격 중심으로 읽게 해요. 섹션마다 강한 카드 경계를 반복하지 않아요. 본문 뒤 ‘PDF로 내보내기’라는 구역 제목 아래 기존 공유/인쇄/저장 버튼을 배치하고, 목록 이동과 삭제는 그 아래 별도 관리 영역으로 구분해요.

**재검토:** 세 PDF 기능을 작은 아이콘 세 개로 압축하면 의미와 터치 영역이 약해져요. 글자와 버튼 형태를 유지하고 좁은 화면에서는 세로로 배치해요. 기능을 새 더보기 메뉴 뒤로 숨기지 않아요. 근거 목록을 다시 추가하지 않으며 PDF 내용 변경도 별도 검증 없이 수행하지 않아요.

관련: `features/records/report-content.tsx`, `reports-screen.tsx`, `report-html.ts`.

### 13. AI 이용 설정과 동의

**질문:** 설정 화면이 기술 문서를 읽는 화면처럼 느껴지지 않나요?

**제안:** 동의 전, 코드 미등록, 준비 완료의 기존 세 상태를 명확한 상태 제목으로 보여줘요. 코드 입력란에는 지속적으로 보이는 라벨을 두고 등록을 주요 버튼으로 표현해요. 등록 완료 상태는 입력 폼을 숨기는 현재 정책을 유지하고, 코드 삭제/동의 철회 두 관리 버튼의 범위를 설명해요.

**재검토:** 준비 완료를 보여주면서 위험 관리 버튼까지 성공을 뜻하는 녹색으로 채우지 않아요. 동의 모달의 거절도 충분히 분명한 버튼으로 표시하고, 긴 설명을 작게 줄이거나 숨기지 않아요. 코드 입력, 검증, 전송 동의와 배치는 계속 분리해요. 설정 메뉴 위치와 공개 정책도 바꾸지 않아요.

관련: `features/settings/ai-settings-screen.tsx`, `features/records/ai-controls.tsx`.

### 14. 일반 설정과 개발자 설정

**질문:** 화살표가 있다는 이유만으로 배경 없는 메뉴가 충분히 알아보기 쉬운가요?

**답:** 현재 사용자 요구에는 부족해요. 메뉴 전체가 하나의 경계 있는 흰색 그룹에 속하도록 정리하는 편이 좋아요.

**제안:** 알림은 스위치 그룹, 앱 안내와 개인정보는 이동 메뉴 그룹, 초기화는 위험 영역, 개발자는 하단 보조 메뉴 그룹으로 나눠요. 각 행에 매번 둥근 카드를 씌우기보다 하나의 그룹 안에서 구분선과 넉넉한 터치 영역을 사용해요. 버전은 현재처럼 작은 비조작 보조 정보로 유지해요.

개발자 설정에서도 첫 실행 체험/AI 설정/가상 자료의 구분은 유지해요. 가상 자료 영역은 개발용임을 표시하되 일반 기능보다 과하게 강조하지 않아요.

**재검토:** 디자인 통일을 이유로 개발자 기능을 일반 설정으로 끌어올리지 않아요. 초기화를 녹색 주 버튼으로 만들지 않아요. 새 설정이나 앱 정보 상세 화면을 추가하지 않아요.

관련: `app/(tabs)/settings.tsx`, `features/settings/developer-settings-screen.tsx`, `features/reset/settings-reset.tsx`.

### 15. FAQ, 앱 안내, 개인정보 문서

**질문:** FAQ의 글과 버튼을 크게 만들면 문서 전체도 카드에 담아야 하나요?

**답:** 아니에요. 문서는 읽기 위주, FAQ는 펼치기 위주로 표현해요.

**제안:** FAQ 질문은 경계 있는 목록 그룹과 펼침 화살표로 표시하고, 답은 일정한 들여쓰기/문단 간격으로 보여줘요. 연결된 기능과 공식 링크는 구별되는 보조 버튼으로 보여줘요. 앱 안내와 개인정보는 소제목과 본문 중심으로 두고 문단마다 카드를 추가하지 않아요.

**재검토:** 출처와 법적 내용을 화면이 길다는 이유로 삭제하지 않아요. 공식 링크의 목적지 이름과 외부 이동 표시를 유지해요. 이메일/문서 링크도 눌러야 하는 영역은 분명하게 보여줘요.

관련: `features/faq/screen.tsx`, `features/settings/app-notices-screen.tsx`, `features/privacy/privacy-screen.tsx`, `components/official-source-links.tsx`.

### 16. 날짜, 시간, 알림 설정

**질문:** 달력과 시간휠의 외형만 통일하면 정확성도 해결되나요?

**답:** 아니에요. 시각적인 배치와 저장값 일치는 따로 검증해야 해요.

**제안:** 중복 카드 여백을 줄여 날짜 폭을 확보하고, 선택일을 명확한 정보 영역으로 표시해요. 시간 입력은 경계 있는 이동 버튼, 시간 선택창은 현재 선택 시간이 알아보기 쉬운 구조로 정리해요. 알림 설정의 스위치는 영역 안에서 제목과 연결해요.

**재검토:** 320px에 7개 48px 날짜를 억지로 넣거나 터치 영역을 겹치지 않아요. iOS/Android 시간휠의 스크롤/선택/완료 동작은 실제 기기 확인이 필요해요. 날짜 미정과 시간 미정 기능을 디자인 변경으로 없애지 않아요.

관련: `components/month-grid.tsx`, `visit-time-picker.tsx`, `app/visit.tsx`, `features/notifications/provider.tsx`.

### 17. 팝업, 대기, 오류, 빈 화면

**질문:** 성공, 오류, 일반 안내가 모두 같은 연녹색 박스면 구분되나요?

**제안:** 제목과 문구로 먼저 구분하고 필요할 때 작은 상태 아이콘/색을 보조로 사용해요. 오류에는 보존되는 데이터와 다음 행동을, 빈 화면에는 데이터가 없는 이유를 보여줘요. 생성 중에는 실제 진행 단계와 기다린 시간만 보여줘요. 팝업은 제목/본문/행동 영역의 간격을 맞추고 버튼을 긴 본문 끝에서 찾기 어렵지 않은지 확인해요.

**재검토:** 모든 오류를 빨간 큰 배너로 만들지 않아요. 사용자 취소는 오류로 표시하지 않아요. 동의/삭제/저장 실패 팝업은 중요도가 다르므로 외형을 통일하더라도 안전한 선택과 기존 동작을 보존해요. 모달 초점과 최대 글자 크기는 실기기 검증 전 완료로 판단하지 않아요.

관련: `components/navigation/overflow-menu.tsx`, `app-header.tsx`, `features/records/report-progress.tsx`, 각 기능의 오류 분기.

## 공통 컴포넌트 적용 전 주의점

1. `styles.link`를 바꾸는 것만으로 모든 보조 행동이 바뀌지 않아요. 인라인 투명 배경과 별도 Pressable이 많아 실제 사용처를 함께 점검해야 해요.
2. 반대로 공통 스타일 하나에 강한 테두리를 넣으면 메뉴, 외부 링크, 보조 버튼이 모두 같은 무게가 돼요. 실행/이동/펼치기/상태의 역할별 스타일을 분리하는 편이 안전해요.
3. 기존 `unknown`은 미응답과 명시적 불확실성이 섞일 수 있어요. ‘아직 답하지 않았어요’를 무조건 매핑하지 않아요. 답변 이력 확인 없이 상태 의미를 재해석하지 않아요.
4. 표시상의 명확함 때문에 저장값, 선택 가능한 답변, 설문 순서, AI 호출 시점을 바꾸면 이번 디자인 범위를 벗어나요.
5. 버튼 그룹을 한 줄로 만들더라도 긴 한국어와 큰 글자에서는 세로로 자연스럽게 전환해야 해요. 버튼 높이를 고정해 문구를 자르지 않아요.

## 실제 적용 시 검수 기준

- 화면 유형별로 홈, 선택 질문, 직접 입력, 기록 상세, 보고서 상세, 설정, 긴 팝업을 대표 화면으로 먼저 정돈해요. 다른 화면에는 같은 규칙을 적용하되 역할을 유지해요.
- 320/390/430px와 iOS/Android 글자 확대에서 제목, 버튼, 상태, 달력을 확인해요. 모든 폭에서 같은 줄 수를 강요하지 않아요.
- 정상 화면뿐 아니라 비활성, 선택, 누름, 로딩, 실패, 자료 없음, 긴 내용, 키보드, 동의 철회, 저장 완료 상태를 확인해요.
- 각 변경 전후의 화면 행동과 저장 결과를 대조해요. 디자인 변경이 AI 재요청이나 원본 수정으로 이어지면 안 돼요.
- iPhone과 Android 실기기에서 확인하지 않은 키보드, 시스템 뒤로가기, 스크린리더, PDF 공유/인쇄는 미검증으로 남겨요.

## 최종 의견

모든 화면을 홈처럼 흰 카드와 녹색 테두리로 채우는 방식은 권하지 않아요. 같은 색과 글씨 체계 안에서 **메뉴는 이동하기 쉽게, 질문은 선택하기 쉽게, 입력은 작성하기 쉽게, 보고서는 읽기 쉽게** 표현해야 전체 앱이 정돈돼 보여요.

이번 검토의 우선 대상은 경계 없는 보조 행동, 상태와 버튼의 혼용, 보고서 관리 버튼의 반복, 문단마다 같은 카드 사용이에요. 앱 코드와 Worker는 수정하지 않았어요. Workers 재배포도 필요하지 않아요.
